# Changelog

All notable changes to BlueFairy API Gateway are documented here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).
Versioning follows [Semantic Versioning](https://semver.org/): major = architecture change, minor = new feature, patch = bug fix or security fix.

## [Unreleased]

### Changed
- Performance (review batch 6). **DB version 1.0.2**: the deliveries table gains `idx_status_retry (status, next_retry_at)` and `idx_webhook_dir_id (webhook_id, direction, id)` — the Webhooks tab's one-query last-status read is a loose index scan again (1.28 ms, not 1.5 s, on 300k rows) — and the upgrade nulls `next_retry_at` on every finished row; from now on a finished or resent delivery clears it, so the pending-flush sweep reads only live rows and a row mid-retry can no longer be sent twice by the flush cron. The shutdown flush sends for at most fifteen seconds of wall clock before queueing the rest; the flush cron drains batch after batch for up to twenty seconds a run and re-arms only while rows remain; a queued row's webhook comes from the cached enabled list, not a query per row. A request refused from the rate-limit marker now fires **`bfag_rate_limit_refused( $subject, $rule, $ip, $refused_so_far )`** with the running count of refusals this window (kept in the marker, no query) — `bfag_rate_limit_breached` still fires once per window, when the subject newly breaches; `RateLimitMiddleware::refused_count()` reads the count. A broken install (`bfag_install_error`) is retried at most once per five minutes instead of on every boot (WPMAP-115), and the error option is rewritten only when its content changes or a retry is due; network activation lifts the time limit and suspends cache addition while it walks the sites, and always restores the current site. The transient prune runs in slices of 1,000 pairs (not 5,000) and sweeps every expired `bfag…` transient — limited markers, parked forms, secrets, Pro's `bfagp_` ones — not only the responses. The hits-table cap reads `MAX(id) - MIN(id) + 1` instead of the engine's row estimate (stale for up to a day on MySQL 8). The cache-stats flush covers every bucket a counter can still live in (a late cron lost one) and takes a 30-second lock so the dashboard Refresh and the cron cannot both flush. The refused-form transient is keyed per tab (`bfag_form_<user_id>_<tab>`); uninstall removes the per-user proxy-notice dismissal; `bfag_kpis` is no longer listed as an option (it is a transient); `CacheStore::delete()` (no caller) is gone. `EventBus` takes an optional clock closure as its fifth constructor argument. The test harness defaults `wp_is_serving_rest_request()` to false, renders dates in the site's `timezone_string`, keys recurring cron events by args, reads `BFAG_DB_VERSION` from the plugin file, and the nonce scanner checks every arm of a multi-method route.
- Usability (review batch 4c). The rate-limit **Penalty** row appears for Pro only and only for *Count by: IP address* (it is hidden and disabled for per-user/per-key rules, and stored as 0 for them — the Pro mitigator bans IP addresses only). *Default TTL* is now **New-rule TTL**: it pre-fills a new cache rule's TTL and is no longer a fallback (`CacheManager::ttl_for()` returns the rule's TTL, clamped). **Retry** is offered only on `failed`/`retrying` outbound deliveries, and `bfag_ajax_retry_webhook` refuses any other status with 400. A refused save keeps what was typed for one re-render of the form (transient `bfag_form_<user_id>_<tab>`, 60 s) and the notice names the cause: `webhook_url_invalid`, `webhook_label_invalid`, `webhook_event_invalid` (was `webhook_event_unknown`), `ratelimit_glob_invalid`, `ratelimit_range_invalid`; `cache_invalid` lists the glob's real character class. Every timestamp is rendered through `Page::format_datetime()` in the site's timezone and formats, with *(site time)* in the column header. The free dashboard's third card is **Blocked (Pro)** (`—`, *Bans need the Pro add-on*); with Pro it is **Active bans** (or the KPI array's `blocked_label`). `bfag_cache_page_after` / `bfag_ratelimit_page_after` fire after the add/edit form, not between the table and the form. The dashboard Refresh replaces *Not computed yet* with *Updated just now*. Copy and accessibility: the rate-limit *Count by* column uses the form labels; the WP-Cron notice says where the box is; the status-endpoint note names Application Passwords / API keys; Max retries has help text; every rules table has a screen-reader caption and `scope="col"` headers; the Enabled/Disabled badges carry `role="button"`, `aria-pressed` and a title; the Settings tab hides *Notification email* / *Failure threshold* (as hidden values) unless Pro is active.
- `Capabilities::request_allowed( $request )` is the permission callback of `/bfag/v1/status` and `/bfag/v1/cache/purge`: the manage capability, or an API key (Pro) whose scope covers the route — so a `cache:purge` key bound to no user can purge. `CacheController` takes a `CachePurger`.
- One purge entry point: `CachePurger` is service `cache.purger`; the Cache tab, the AJAX purge and the REST endpoint all go through `purge_all()` / `purge_tags()` (which now returns the tags bumped), so `bfag_cache_purged` fires once per purge and a tag no enabled rule carries is dropped whoever names it.
- `bfag_webhook_request_args` may set `Authorization`; everything else it plants in `headers` is sanitised again (a `Host`, `X-Forwarded-*` or CR/LF value is stripped). Setting `$args['bfag_skip']` to a non-empty string cancels the delivery: recorded `failed` with that reason, nothing sent, `bfag_webhook_delivery_failed` fired. `WebhookDispatcher` takes the shared `WebhookRepository` as an optional third constructor argument.
- `Installer::deactivate( bool $network_wide = false )` unprovisions every site on a network deactivation; `maybe_upgrade()` rewrites `bfag_version` whenever it differs. `Logger` keeps at most 200 lines in memory (the oldest are dropped; the error log still gets every line). `EventRegistry::label()` / `group_label()` and `Capabilities::scope_label()` return translatable text; the views use them. `AdminMenu` takes the `CachePurger` and the one `KpiCron` from `Plugin::boot()` (service `kpi.cron`) instead of a `CacheStore`, `CacheStatsRepository` and `HitCounter`.
- The seeded rate-limit rule is now 300 requests per 60 s per IP (was 60), and logged-in users who can edit posts are exempt from rate limiting by default (new setting *Exempt editors*, `rate_limit_exempt_editors`).
- The limiter ignores dispatches that are not the top-level HTTP REST request — WP-CLI, WP-Cron and internal `rest_do_request()` calls from admin-ajax or the front end — so a penalty rule can no longer ban the server's own loopback address. Requests with no resolvable client IP are not counted.
- `AdminMenu::handle_actions()` acts only on the plugin's own screen for a user who can manage the gateway, checked before the nonce; a stray `bfag_action` on another admin page is ignored instead of ending in `wp_die`.

- Performance (review batch 4b). Without a persistent object cache, stored responses are capped at 64 KB and one hour and expired transients are swept every five minutes (`bfag_cron_prune_responses`); the Settings → Cache group says so. A client over a limit is refused from a marker for the rest of its window with no hit-log INSERT or COUNT. With a persistent object cache the rate-limit count is a `wp_cache_incr()` in fixed windows (the hit row is still written) and the cache hit/miss counters are object-cache increments flushed by the KPI cron, so a cache HIT costs one query. `bfag_tag_generations` holds only tags enabled rules carry. The shutdown flush sends at most twenty deliveries (five-second timeout) and queues the rest for a `bfag_cron_flush_pending` single event; under WP-CLI/WP-Cron the queue is flushed past twenty; under PHP-FPM the response is finished first (`bfag_webhook_finish_response` filter). The Webhooks tab reads every last status in one query; `recent()` is one literal statement ordered by `created_at DESC, id DESC`; the dashboard and `/bfag/v1/status` take their counts from the KPI transient (`counts.cache_24h`/`deliveries_24h` are `null` until the first KPI run; new KPI key `webhook_deliveries`); the hits-table cap check reads the engine's row estimate; the daily prune also removes `pending`/`retrying` rows older than a day; the `route` column is written capped at 191 characters. DB version 1.0.1 adds `idx_webhook_id` and `idx_created_at` to the deliveries table. `EventBus` takes a `DeliveryRepository`; `StatusController` takes only the `WebhookRepository`; `DashboardPage` no longer takes a `HitCounter`.

### Added
- `tests/js/admin.test.js` (`node tests/js/admin.test.js`), `tests/Unit/PluginTest.php` (boot order, service ids), an ordering rule in `AdminNonceCoverageTest` (capability check before the first superglobal read or repository call).
- Multisite: a network-wide activation provisions every site (tables, seeded rules, capability, settings, crons); a site created afterwards is provisioned on `wp_initialize_site`; a site with no DB version is provisioned on its first boot.
- Table creation is verified with `SHOW TABLES` after `dbDelta`. A missing table is written to the PHP error log, recorded in `bfag_install_error`, shown as an admin notice on every screen, and the DB version is not recorded so the next boot retries.
- A dismissible notice on the plugin's screen, the Plugins screen and the Dashboard when a forwarded-address header arrives and no trusted proxies are configured (every visitor would share one rate-limit bucket).
- Help text for the trusted-proxies setting and the seeded rule.

### Removed
- `bfag_webhook_auth_headers` (no consumer; `Authorization` comes through `bfag_webhook_request_args`), `CacheStatsRepository::hit_rate()`, `EventBus::invalidate()`, `AdminMenu::page()`, `Settings::refresh()` and the unreachable `Installer::check_requirements()`.

## [1.0.0] — 2026-09-30

Initial release. The free base plugin of a pair; BlueFairy API Gateway Pro is an add-on that attaches to the `bfag_*` seams listed in `FEATURES.md`.

### Added
- **REST response cache.** Anonymous `GET`/`HEAD` responses are stored and served from `rest_pre_dispatch`, and every REST response carries `X-BF-Cache: HIT`, `MISS` or `BYPASS`. Requests from logged-in users or carrying `Authorization`, `X-BF-API-Key` or `X-WP-Nonce` are never cached; responses that are not 2xx, that stream, that set a cookie or that say `no-store`/`private` are never stored. The plugin's own `/bfag/v1` routes are excluded.
- Cache rules matched by route glob (`*` one segment, `**` anything, `?` one character), with a TTL (1–86400 s) and tags; one rule in the free plugin, seeded as `**` / 60 s on activation. Rules are the allow-list.
- Storage in the object-cache group `bfag_responses` when a persistent object cache is present, otherwise in `bfag_resp_*` transients. Purging is O(1) through generation numbers embedded in every key; no entry is ever enumerated.
- Automatic purge when a post is saved, trashed or deleted (revisions and autosaves ignored), a term is created, edited or deleted, or a comment is inserted or changes status. Manual purge from the Cache tab (**Purge all**), by AJAX, and through `POST /bfag/v1/cache/purge` with optional `tags`.
- Cache hit and miss counters in five-minute buckets (`bfag_cache_stats`).
- **Rate limiting.** A sliding-window counter per client IP and route on `rest_pre_dispatch` at priority 5, ahead of the cache. Insert-then-count, so concurrent requests cannot all slip under the limit together. The breaching request answers `429 bfag_rate_limited` with `Retry-After`, `X-BF-RateLimit-Limit` and `X-BF-RateLimit-Window`. Fails open on a database fault.
- Rate-limit rules by route glob with a request count (1–65535) and a window (1–86400 s); out-of-range values are rejected, not clamped. One rule in the free plugin, seeded as 60 per 60 s on `**`. `GET /bfag/v1/status` is exempt.
- Client IP resolution behind trusted proxies: `CF-Connecting-IP`, `X-Real-IP` and `X-Forwarded-For` are honoured only when `REMOTE_ADDR` is inside a configured proxy range, taking the right-most forwarded address that is not itself a proxy.
- Hit-log pruning every five minutes (10,000 rows per batch, up to 50 batches) and a hard cap that truncates the table past ten million rows.
- **Outbound webhooks.** Up to three in the free plugin, each subscribing to one event: `post.published`, `post.updated`, `post.deleted`, `user.registered`, `user.updated`, `comment.created`, and — while WooCommerce is active — `woocommerce.order.created`, `woocommerce.order.status_changed`, `woocommerce.order.completed`, `woocommerce.product.updated`. Payloads are built from an allow-list of fields per object; no password hashes, no `$_SERVER`, no other users' emails.
- Each delivery is a JSON `POST` with `Content-Type`, `User-Agent: BlueFairy-API-Gateway/1.0.0`, `X-BF-Event`, `X-BF-Delivery`, `X-BF-Timestamp` and `X-BF-Signature: sha256=HMAC-SHA256(timestamp.body, secret)`. Sent through `wp_remote_post()` with a ten-second timeout, no redirects and `reject_unsafe_urls`.
- Webhook targets must be `https://` and pass `wp_http_validate_url()`; a blank secret is replaced by a random 64-character one and the stored secret is never displayed. Custom headers are sanitised at send time: `Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Cookie`, `Authorization`, `Proxy-Authorization`, `X-Forwarded-*`, line breaks and the plugin's own header names are dropped.
- Events are collected during the request, deduped per event and object id, and delivered once on `shutdown` after the response is sent; a re-entrancy guard stops a receiver's write-back from triggering another delivery. WordPress actions are attached only for events that have an enabled webhook.
- A delivery log with status, HTTP status, the first 2,000 characters of the response, attempt number and timestamps; **Send test** on each webhook; **Retry** on any failed, non-truncated outgoing delivery. Stored payloads are capped at a configurable size and flagged *truncated* beyond it. Finished deliveries older than the retention setting are pruned daily.
- **Dashboard** with cache hit rate, webhook success rate and hit-log size over 24 hours (recomputed every five minutes into a transient, or on demand with **Refresh**), the ten most recent failed deliveries, row counts and a copyable status URL.
- `GET /bfag/v1/status` for monitors and `POST /bfag/v1/cache/purge`, both gated by the `bfag_manage_gateway` capability, which is granted to administrators on activation.
- Settings tab: notification email and failure threshold (stored for the Pro add-on), cache on/off and default TTL, rate limiting on/off and trusted proxies, max stored payload and delivery-log retention, debug logging, a switch to hide the WP-Cron warning, and *Delete data on uninstall*.
- Thirty-three documented `bfag_*` actions and filters as the add-on contract, and `Plugin::service()` for shared instances.
- `uninstall.php` removes options, transients, cron events and the capability on every site; drops the six tables only when *Delete data on uninstall* is on.
- Compatibility: tested against WordPress 7.1; requires PHP 8.1 or newer.
