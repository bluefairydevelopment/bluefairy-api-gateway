# BlueFairy API Gateway — architecture and module contracts

Base plugin (`bluefairy-api-gateway`, namespace `BlueFairy\ApiGateway`, prefix `bfag_`).
The Pro add-on (`bluefairy-api-gateway-pro`, `BlueFairy\ApiGatewayPro`, `bfagp_`) hooks the
seams listed under **Extension seams** and never ships inside this plugin.

Plan: `~/Sites/blueSites/plans/bluefairy-api-gateway.plan.md` (read "Revision v3" first).

## Fixed conventions

- `declare(strict_types=1);` on line 2 of every PHP file. WPCS (`phpcs.xml.dist`), PHPStan
  level 6 (`phpstan.neon`), PHPUnit 10 (`phpunit.xml.dist`). Tabs. Yoda conditions.
  Every function has a docblock with `@param` for every parameter.
- PSR-4 under `includes/`. Instance-based services wired in `Plugin::boot()`; only
  `Plugin::boot/service/set`, `Installer::*`, `Capabilities::*`, `Logger::*`,
  `GlobMatcher::*`, `IpUtils::*` and `CacheStore::sanitize_tag()` are static.
- Option writes whose outcome matters go through the trait `Support\WritesOptions::write_option( $option, $value, $autoload ): bool` (F21 / WPMAP-110): `update_option()` returns false both for a refused write and for an unchanged value, so on false the stored value is read back and compared in its stored form (`maybe_serialize`). Used by `Settings`, `CacheStore` and `WebhookRepository`.
- All SQL through `$wpdb->prepare()`; reads via `get_results/get_row/get_var/get_col`;
  writes via `insert/update/delete` or prepared `query()`. Table names are
  `$wpdb->prefix . 'bfag_…'`. Every list query has a `LIMIT`.
- **One row ceiling (WPMAP-138):** `Support\Limits::MAX_ROWS` (1000, at least `Limits::DEFAULT_LIMIT`) bounds every read of the
  cache-rule, rate-limit-rule and webhook tables — `all_enabled()` (the enforcement read), `all()` (the admin lists, and Pro's
  `GET /bfag/v1/webhooks`, which calls it with no argument) and `enabled_events()` — and `Limits::clamp()` bounds every `limit()` to
  0..MAX_ROWS, so a row that may be created is always one that is listed, matched and enforced. (The reads stopped at `LIMIT 200`
  while Pro allowed 500: rules 201-500 counted toward the limit but never appeared and never matched.)
- **One default limit (WPMAP-142):** `Support\Limits::DEFAULT_LIMIT` (500) is the default of all three limit filters
  (`bfag_cache_rule_limit`, `bfag_rate_limit_rule_limit`, `bfag_webhook_limit`; 1, 1 and 3 before 1.0.1), with or without
  the Pro add-on — an engineering bound, not a paid tier (WordPress.org guideline 5). Pro attaches nothing to them on a 1.0.1+
  base. At the limit the add form gives way to `Page::limit_line( string $what ): string` (*This site allows %s and all of
  them are in use. Edit or delete one to add another.*), and a refused add redirects with `cache_limit` / `ratelimit_limit` /
  `webhook_limit`, whose notices name the site's limit; none of the three mentions Pro.
- Hot-path reads (`all_enabled()`) are object-cached in group `bfag`, key named below,
  TTL 300, and every write to that table calls `wp_cache_delete()` on the key.
- Admin: every form handler calls `check_admin_referer( 'bfag_<action>' )` and
  `current_user_can( Capabilities::MANAGE )`; every AJAX handler calls
  `check_ajax_referer( 'bfag_ajax_<action>', 'nonce' )` and the same capability.
- Output escaped at the boundary (`esc_html`, `esc_attr`, `esc_url`, `wp_kses_post`).
- Text domain `bluefairy-api-gateway`. Prefix every global (`bfag_`), hook (`bfag_`),
  option (`bfag_`), transient (`bfag_`), cron (`bfag_cron_`), AJAX action (`bfag_ajax_`),
  handle (`bfag-`), capability (`bfag_manage_gateway`), REST namespace `bfag/v1`.
- Logging: `Logger::log( string $message, array $context )`, only when debug_logging is on.
- No third-party SDKs or Composer runtime dependencies. HTTP only via `wp_remote_*`.

## Module contracts

Constructor signatures and the methods `Plugin::boot()` and the other modules call. Add
private helpers freely; do not rename or re-type anything here without updating
`Plugin.php`, this file and the tests.

### Cache (`includes/Cache/`)

**`CacheStore`** — `__construct()`. Stores serialised REST responses. Backend: WP object
cache group `bfag_responses` when `wp_using_ext_object_cache()`; otherwise transients
`bfag_resp_<key>`. Generations make purging O(1) on both backends: an entry's key embeds the
global generation and the generation of every tag the matching rule carries, so bumping a
generation orphans the old entries (transients expire by TTL; object-cache entries by TTL).
- `get( string $key ): ?array` — `['status'=>int,'headers'=>array,'data'=>mixed,'stored_at'=>int]` or null
- `set( string $key, array $entry, int $ttl ): void` — on the transient backend the TTL is capped at `MAX_TRANSIENT_TTL` (3600 s: a purge only orphans a transient, its md5 key hides the generation, and core sweeps expired transients once a day — the cap bounds how long an orphan occupies two options rows) and an entry whose serialised size exceeds `MAX_TRANSIENT_BYTES` (65536) is not stored (logged once per request). No cap on the object cache
- `prune_expired(): int` — transient backend only: `SELECT option_name … LIKE '_transient_timeout_bfag%' AND option_value < now LIMIT PRUNE_BATCH` (1000 — a 5,000-name DELETE was a 600 KB, one-second statement, PN7), then one `DELETE … WHERE option_name IN (…)` of both rows of each pair, looping until a short slice (max `PRUNE_MAX_ITERATIONS` = 20). The LIKE is `PRUNE_PREFIX` = `bfag`, so every expired transient of the plugin family — limited markers, parked forms, one-time secrets, the Pro add-on's `bfagp_` ones — goes with the responses instead of waiting for core's daily sweep (PN11). Returns pairs deleted. Run by `Cache\PruneCron`. (There is no per-key `delete()`: entries are orphaned by generation, never deleted one by one — N-12.)
- `generation(): int` — option `bfag_cache_generation` (autoloaded; object-cached in group `bfag`, key `generation`)
- `flush_all(): bool` — increments `bfag_cache_generation` (written with autoload `true`), clears the `bfag_responses` group when supported. Returns false (and logs) when nothing was purged: the generation write was refused AND no persistent response group was flushed in its place (F21 / WPMAP-110 — `void` before; a caller ignoring the result is unaffected)
- `tag_generation( string $tag ): int` — read from option `bfag_tag_generations` (array `tag => int`, autoload false; default 1), through a per-request memo and object-cache group `bfag` key `tag_generations`. One option so uninstall can delete it by name: a transient per tag lived in an external object cache's `transient` group, which `uninstall.php` cannot enumerate
- `bump_tags( string[] $tags, ?string[] $keep = null ): bool` — false (logged) when the option write was refused, true otherwise (also when nothing changed) (F21; was `void`); increments each entry, writes the option once, deletes the object-cache key and the memo. With `$keep` (the tags enabled rules carry, which `CachePurger` passes) every stored generation not in it is dropped, so the option holds at most rules × tags entries instead of one per object ever saved; a dropped tag restarts at 1, so the global generation is bumped too (`flush_all()`), and a rule that later carries that tag again can never meet an entry keyed on the old generation 1
- `CacheStore::sanitize_tag( string $tag ): string` — static; the one tag sanitiser (`[a-z0-9_:-]`, lower-cased, max 50). Every purge path (REST, AJAX, rule tags) uses it; `sanitize_key()` must not be used on a tag because it strips the `:` of `post:42`.

**`Cache\PruneCron`** — `__construct( CacheStore )`. `register_hooks()` adds `bfag_cron_prune_responses` → `run()`: `prune_expired()`, logged.

**`CacheKeyGenerator`** — `__construct( CacheStore )`.
- `for_request( \WP_REST_Request $request, string[] $tags = [] ): string` — `md5()` of
  method + route + ksorted query params + lowercase `Accept` header + global generation +
  each tag's generation. Params `_wpnonce`, `_locale` excluded.
- `CacheKeyGenerator::IMPLICIT_TAG` = `'all'`. **An empty `$tags` is keyed as `[ 'all' ]`**: a rule with no tags is purged on every content change (the Pro purge-tag answer always includes `all`); add tags to narrow purging to those tags. Tagged rules do NOT get `all` added — that is what makes them narrower. `purge_all()` still bumps the global generation (flushes everything, tagged or not).

**`CacheRuleRepository`** — `__construct()`. Rows are associative arrays with the table's
columns, `enabled`/`id`/`ttl_seconds` cast to int, `tags` as a comma-separated string.
- `all_enabled(): array` — object cache key `cache_rules_enabled`, ordered by id
- `all( int $limit = Limits::MAX_ROWS ): array` (clamped to 1..MAX_ROWS), `find( int $id ): ?array`, `count(): int`
- `create( array $data ): int|false` — returns false (and logs) when `count() >= limit()` or the glob fails `GlobMatcher::is_valid`; the TTL is **clamped** to 1–86400 (never refused), and `update()` clamps it the same way; tags sanitised through `CacheStore::sanitize_tag()` (`[a-z0-9_:-]`, lower-cased, max 50 chars, max 20 tags; `post:7`, `type:product` are the Pro purge-tag shapes)
- `update( int $id, array $data ): bool`, `delete( int $id ): bool`, `set_enabled( int $id, bool ): bool`
- `limit(): int` — `Limits::clamp( apply_filters( 'bfag_cache_rule_limit', Limits::DEFAULT_LIMIT ) )`
- `match( string $route ): ?array` — among enabled rules whose glob matches (via `GlobMatcher`) the most specific one: highest `GlobMatcher::specificity()`, tie → lowest id; null when none. So a `wp/v2/posts/**` rule added after the seeded `**` rule wins for posts
- `sort_by_specificity( array $rules ): array` — the same order, for the Cache tab ("Most specific rule wins")
- `tags_of( array $rule ): string[]`

**`CacheStatsRepository`** — `__construct()`.
- `record_hit(): void`, `record_miss(): void` — `INSERT … ON DUPLICATE KEY UPDATE` into the current 5-minute bucket (`gmdate` floored to 300 s). With a persistent object cache (`true === wp_using_ext_object_cache()`) no query: `wp_cache_add` + `wp_cache_incr` on `counter_key( $bucket_start, 'hits'|'misses' )` = `stats:<bucket>:<kind>` in group `bfag`, TTL `COUNTER_TTL` (900 s)
- `flush_counters(): int` — persistent cache only: for every bucket from `now − COUNTER_TTL` to the current one (four, so a late cron loses none — PN10), read both counters, one `INSERT … ON DUPLICATE KEY UPDATE hits = hits + %d, misses = misses + %d` when either is non-zero, then `wp_cache_decr` each by what was written (hits counted during the flush survive). One flush at a time: `wp_cache_add( FLUSH_LOCK_KEY = 'stats:flush_lock', 1, 'bfag', FLUSH_LOCK_TTL = 30 )` is taken first and a caller that cannot take it returns 0 (the dashboard Refresh and the cron racing would write a counter twice and decrement it below zero). A failed upsert leaves the counters for the next run. `KpiCron::run()` calls it before aggregating, so with a persistent cache `totals_since()` lags the live traffic by at most one cron interval
- `totals_since( string $mysql_gmt_datetime ): array{hits:int,misses:int}`
- `prune( int $keep_days = 7 ): int`

**`CacheManager`** — `__construct( CacheStore, CacheKeyGenerator, CacheRuleRepository, CacheStatsRepository, Settings, ?\Closure $sent_headers = null )` — the closure returns the raw header lines PHP has queued (null = `headers_list()`; a test seam, since the CLI SAPI records no headers).
- `register_hooks(): void` — `rest_pre_dispatch` (priority 10, 3 args) → `maybe_serve()`, `rest_post_dispatch` (10, 3 args) → `maybe_store()`
- No matching enabled rule → BYPASS (rules are the allow-list; the seeded `**` rule covers everything).
- `maybe_serve( mixed $result, \WP_REST_Server $server, \WP_REST_Request $request ): mixed` — returns a `\WP_REST_Response` rebuilt from the entry (status, headers, data) with header `X-BF-Cache: HIT`, else `$result` unchanged
- `maybe_store( \WP_HTTP_Response $response, \WP_REST_Server $server, \WP_REST_Request $request ): \WP_HTTP_Response` — a bare `WP_HTTP_Response` is returned untouched; a `WP_REST_Response` is stored when cacheable, adds `X-BF-Cache: MISS` (or `BYPASS` when not cacheable), adds any `headers` JSON from the rule
- `is_cacheable_request( \WP_REST_Request ): bool` — `cache_enabled` on; GET or HEAD; not logged in (`is_user_logged_in()`); no `Authorization`, `X-BF-API-Key`, `X-WP-Nonce` header; route not under `/bfag/v1` (compared lower-cased: core matches routes case-insensitively); `apply_filters( 'bfag_cache_bypass', false, $request )` false
- `is_cacheable_response( \WP_REST_Response ): bool` — status 200–299, `Content-Type` not `text/event-stream`, no `Set-Cookie` in the response headers NOR in PHP's queued headers (`headers_list()` — U-22 / WPMAP-111: core and WooCommerce call `setcookie()`, which never reaches the `WP_REST_Response`; `rest_post_dispatch` runs before `WP_REST_Server` sends anything, so a callback's cookie is visible here, while one set after this filter is not, and one set for every visitor earlier in the request keeps every response from being stored), no `Cache-Control` directive `no-store`, `private` or `no-cache`, and no `max-age=0` / `s-maxage=0` (directives are split on commas and compared by name)
- `ttl_for( ?array $rule ): int` — the rule's `ttl_seconds` clamped to 1–86400 (a rule always carries one); `default_cache_ttl` is NOT a fallback — it only pre-fills the TTL of the add-rule form (U-09)

**`CachePurger`** — `__construct( CacheStore, CacheRuleRepository )`. Service `cache.purger`. **The one purge entry point (F11):** the content hooks, the Cache tab's *Purge all*, `AdminMenu::ajax_purge_cache` and `CacheController::purge` all call `purge_all()`/`purge_tags()`, so `bfag_cache_purged` fires from one place and a tag no enabled rule carries is dropped and logged whoever names it.

**`RateLimitRuleRepository`** — same shape as CacheRuleRepository. Object cache key

**`HitCounter`** — `__construct()`.
- `consume( string $subject, string $route, int $window, int $max, ?string $display_route = null ): bool` — `$route` is the **bucket key** (whatever is counted together; the middleware passes `RateLimitMiddleware::bucket( $rule_id )` = `rule:<id>`), hashed into `route_hash`; `$display_route` is what the `route` column shows (the real route, capped at 191 chars), the bucket key when null. INSERT the hit, then `SELECT COUNT(*) … WHERE subject = %s AND route_hash = %s AND hit_at > %s` (window start as GMT datetime); returns true when count > max. `route_hash()` = `substr( hash( 'sha256', $route ), 0, 16 )`, public static. **With a persistent object cache** the INSERT still happens (the admin's hit log reads the table) but the COUNT is replaced by `count_in_window()`.
- `count_in_window( string $subject, string $route, int $window ): int` — `wp_cache_add( key, 0, 'bfag', window × 2 )` then `wp_cache_incr`; `window_key()` = `bfag:rl:<md5(subject|route)>:<floor(time/window)>`, public static. Fixed windows (a subject may get up to 2 × max across one boundary); a failed incr counts as 0 (fail open, like a failed INSERT).
- `count( string $subject, string $route, int $window ): int` — `$route` is the bucket key, as for `consume()`
- `prune( int $max_window ): int` — `DELETE … WHERE hit_at < %s LIMIT 10000` in a loop until 0 rows (max 50 iterations); returns rows deleted
- `total_rows(): int` — exact `COUNT(*)`; the KPI cron's once-per-five-minutes figure
- `approximate_rows(): int` — `SELECT COALESCE(MAX(id) - MIN(id) + 1, 0)`: an upper bound from two index ends, engine-independent (PN9: MySQL 8 caches the `SHOW TABLE STATUS` estimate for up to a day). It over-counts only by rows deleted from the middle of the id range — the prune removes the oldest, and ids rise with `hit_at`, so in practice it is the live count — and never under-counts, so the cap still fires; 0 when there is no such table
- `rotate_if_huge( int $threshold = 10000000 ): bool` — when `approximate_rows()` exceeds threshold: `SELECT MAX(id)`, then `DELETE … WHERE id < MAX(id) - threshold + 1 LIMIT PRUNE_BATCH` in a loop until a short slice (max `PRUNE_MAX_ITERATIONS`), so the newest `threshold` rows remain; logged with `rows`, `threshold`, `deleted`; true when rows were deleted. Never `TRUNCATE` (P17 / WPMAP-108: an exclusive metadata lock stalls every concurrent INSERT and every subject's window resets at once; the range delete locks the oldest ids, far from the end of the primary key where hits are appended). No second COUNT(*) every five minutes

**`RateLimitMiddleware`** — `__construct( RateLimitRuleRepository, HitCounter, Settings, RequestContext )`.
- `register_hooks(): void` — `rest_pre_dispatch` priority 5 (3 args) → `check()`
- `check( mixed $result, \WP_REST_Server $server, \WP_REST_Request $request ): mixed` — if `$result` already non-null, or `rate_limit_enabled` off: return `$result`. Also returned untouched (nothing counted) when the dispatch is not the top-level HTTP REST request: `WP_CLI`, `wp_doing_cron()`, or `wp_is_serving_rest_request()` false AND `REST_REQUEST` unset (an internal `rest_do_request()` from admin-ajax or the front end); when the client IP is empty; and — BEFORE the block filter and before any hits-table work, so an editor behind a blocked shared address keeps working (R2-05) — when `apply_filters( 'bfag_rate_limit_exempt', $exempt, $request )` is true, where `$exempt` = `rate_limit_exempt_editors` on AND a cookie session (`$GLOBALS['wp_rest_auth_cookie'] === true`, set by core only for a valid logged-in cookie that kept its REST nonce) AND logged in with `edit_posts` — an application password or an API key is never exempt (WPMAP-295); Pro answers false whenever a key authenticated the request. The route is normalised once — `strtolower( RequestContext::normalize_route( $route ) )` — because `WP_REST_Server` matches routes case-insensitively; a route under `bfag/v1/status` (any case) returns `$result`. IP = `RequestContext::client_ip()`; if `apply_filters( 'bfag_rate_limit_is_blocked', false, $ip, $request )` → `blocked_response()`. For each rule in `matching( $route )`: `$subject = apply_filters( 'bfag_rate_limit_subject', $default, $rule['subject_type'], $request, $ip )` where `$default` is the IP for type `ip` and null otherwise; skip rule when subject is null/''; `consume( $subject, RateLimitMiddleware::bucket( $rule['id'] ), $window, $max, $route )` — **the budget is per subject and per rule**, not per path, so `/wp/v2/Posts` and `/wp/v2/posts` share one bucket and a crawl of 10,000 distinct URLs under a `**` rule has one budget; on a NEW breach `do_action( 'bfag_rate_limit_breached', $subject, $rule, $request, $ip, $forwarded_without_proxy )` — the 5th argument is `RequestContext::forwarded_header_present() && ! is_trusted_proxy()`: true means the IP is a proxy's shared address (an unconfigured proxy, or a loopback SSR caller) and the Pro mitigator must not ban it (R2-05) — and return `limited_response( $rule )`. **Limited marker:** a breach stores `limited_key( $subject, $rule_id, $max, $window )` = `limited:<md5(subject|rule:<id>|max|window)>` for `window_seconds` — `wp_cache_set` in group `bfag` with a persistent object cache, else transient `bfag_limited_<key>` — and the marker is checked BEFORE `consume()`, so a known-limited subject gets its 429 with no INSERT, no COUNT, no log line and NO breach action until the window ends (R2-07: the action fires once per window, when the subject newly breaches). The marker's value is `[ 'until' => <unix end of window>, 'refused' => <n> ]`: every request refused from it increments `refused` (a read-modify-write — a running figure, not an audit count) and fires `do_action( 'bfag_rate_limit_refused', $subject, $rule, $ip, $refused_so_far )` with the new total and NO database work (PN1: the Pro mitigator can decide a DDoS block when the count crosses its threshold without a COUNT(*) per 429, so the threshold means "requests over the limit in the window"). A marker from an earlier release (a bare timestamp) reads as zero refusals. The rule's limits are in the key, so editing `max_requests` or `window_seconds` retires every marker the old rule left. Without a persistent object cache the probe is one options-table read per matching rule per request.
- `refused_count( string $subject, int $rule_id ): int` — the marker's `refused` for a subject under an enabled rule (the rule's limits, part of the key, come from `all_enabled()`), 0 when not limited or the rule is not enabled; no query
- `RateLimitMiddleware::bucket( int $rule_id ): string` — `'rule:' . $rule_id` (`BUCKET_PREFIX`), public static: the key under which a rule's hits are counted.
- `RateLimitMiddleware::limited_key( string $subject, int $rule_id, int $max, int $window ): string` — public static, the marker key above.
- `limited_response( array $rule ): \WP_REST_Response` — status 429, `['code'=>'bfag_rate_limited','message'=>…,'data'=>['status'=>429]]`, headers `Retry-After: <window_seconds>`, `X-BF-RateLimit-Limit`, `X-BF-RateLimit-Window`
- `blocked_response(): \WP_REST_Response` — status 403, code `bfag_blocked`

**`PruneCron`** — `__construct( HitCounter, RateLimitRuleRepository )`. `register_hooks()` adds
`bfag_cron_prune_hits` → `run()`: `prune( max_window() )`, then `rotate_if_huge()` (the id-range bound, not a COUNT(*); an oldest-first range delete, not a TRUNCATE).

**`DeliveryRepository`** — `__construct( Settings )`.
- `create( array $data ): int|false` — `payload` is JSON string; truncated to `max_payload_bytes` with `truncated = 1` when longer; `status` default `pending`; `direction` `out`/`in`; `next_retry_at` (GMT datetime string, else null) marks a row queued for the pending-flush cron

- `prune( int $retention_days ): int` — `DELETE … WHERE status IN ('success','failed') AND created_at < %s LIMIT 5000` loop, then the same for `status IN ('pending','retrying')` older than one day whatever the retention (a row the cron never picked up, or a send the process died in, must not live for ever)

- `last_status( int $webhook_id ): ?string`
- `last_statuses( int[] $webhook_ids ): array<int, string>` — one grouped query (`WHERE id IN ( SELECT MAX(id) … WHERE webhook_id IN (…) AND direction = 'out' GROUP BY webhook_id )`), served by `idx_webhook_dir_id (webhook_id, direction, id)` as a loose index scan (PN3); `WebhookPage::render()` uses it so the Webhooks tab is one deliveries query however many rows. `consecutive_failures()` and `last_status()` filter on `webhook_id` and `direction` and order on `id` — the same index

**`WebhookDispatcher`** — `__construct( DeliveryRepository, Settings, ?WebhookRepository = null )` — the shared repository from `Plugin::boot()` (F16); null builds one.
- `dispatch( array $webhook, string $event, array $payload, int $attempt = 1, ?int $delivery_id = null ): array{delivery_id:int, success:bool, http_status:?int}` — `$webhook` may be a full row or an `all_enabled()` summary (no `secret` key): a summary is replaced by `find()` before anything is written — ONE read per delivery sent, none per event considered (WPMAP-117) — and a webhook gone or disabled since the list was cached is skipped (logged; no delivery row, no request; `delivery_id` 0). A full row (Send test, Retry, Pro's scheduler — all pass `find()` rows) is used as given. Then body = `wp_json_encode( $payload )`; headers: `Content-Type: application/json`, `User-Agent: BlueFairy-API-Gateway/<ver>`, `X-BF-Event`, `X-BF-Delivery` (id), `X-BF-Timestamp` (unix), `X-BF-Signature: sha256=<hmac>` over `timestamp . '.' . body` with the webhook secret, plus `sanitize_headers( headers_of( $webhook ) )`; `apply_filters( 'bfag_webhook_request_args', $args, $webhook, $event, $payload )`; then (N5) if `$args['bfag_skip']` is a non-empty string the delivery is recorded `failed` with `response_body` = that string and `http_status` null, nothing is sent and `bfag_webhook_delivery_failed` fires with `$is_final` true (D3); otherwise (F4) `$args['headers']` is run through `sanitize_headers()` again with `Authorization`/`Proxy-Authorization` allowed — the filter is trusted for credentials, not for transport headers, so a `Host`, `X-Forwarded-*` or CR/LF value it plants is stripped and logged; a URL that is empty or fails `wp_http_validate_url()` is recorded `failed` with `response_body` = `Invalid or unsafe URL (nothing sent): <url>` (`(empty)` for none), `http_status` null, and fires `bfag_webhook_delivery_failed` with `$is_final` true (D3: the same URL fails the same way on every retry); `wp_remote_post` with `timeout` `WebhookDispatcher::TIMEOUT` (5 s: up to `EventBus::FLUSH_LIMIT` are sent in a row on shutdown), `redirection` 0, `reject_unsafe_urls` true. Creates the delivery row before sending (status `pending`; a reused `$delivery_id` is flipped to `pending` with `next_retry_at = NULL`), updates it after (`success`/`failed`, `http_status`, `response_body` truncated to 2000 chars, `delivered_at`, `attempt`, and `next_retry_at = NULL` — a finished row is never due again; left set, every finished row stayed in `idx_next_retry` and the pending sweep paid for it, PN2). On non-2xx or `WP_Error`: status `failed`, `do_action( 'bfag_webhook_delivery_failed', $delivery_id, $webhook, $attempt, $http_status, $is_final )` — the fifth argument is `bool $is_final`, true only for the skip and unsafe-URL outcomes above (N-05 / D3) and for any failure of a delivery whose JSON body is longer than `max_payload_bytes` (WPMAP-139: the stored copy is truncated, so no retry could resend it — Pro's scheduler then leaves the row `failed` and its final-failure alert fires instead of the row sitting `retrying` forever). On success `do_action( 'bfag_webhook_delivered', $delivery_id, $webhook )`.
- `redeliver( int $delivery_id, array $webhook ): array` — resend a stored delivery's payload with `attempt + 1`; the row is flipped to `pending` with `next_retry_at = NULL` in the same update, else a `retrying` row mid-redeliver is also what `pending()` selects and the flush cron would send it twice (PN2). Refused (`success` false, logged, nothing sent) when the row is missing, `truncated`, or its `direction` is not `out`. A `truncated` row whose status is `retrying` (a scheduler holds it) is also ended (WPMAP-139): `status = failed`, `next_retry_at = NULL` — its `attempt`, `http_status` and `response_body` stay as recorded — and `bfag_webhook_delivery_failed` fires once with that attempt and status and `$is_final` true; a truncated row in any other status is left untouched and announces nothing (it was announced when it failed). An inbound row is refused because it was written by whoever called the receiving endpoint, and signing it with the site's secret would launder an unverified sender's payload
- `dispatch_pending( array $row ): array` — send a row `EventBus` queued past its flush limit: decides from `WebhookRepository::all_enabled()` (object-cached — a dropped row costs no `find()`, PN4; absent from it = deleted or disabled → row `failed`, nothing sent, logged; a `truncated` payload — the full body lived only in the request that queued it — is finished as a FINAL failure through `finish()` (WPMAP-141): `failed`, `http_status` null, `response_body` = `WebhookDispatcher::TRUNCATED_UNSENT`, `next_retry_at` NULL, and `bfag_webhook_delivery_failed` with `$is_final` true, exactly as an oversized delivery that fails in the shutdown flush, so Pro's scheduler leaves it and its alert fires), then reads the credentials of the one it sends with `find()` (WPMAP-117; gone or disabled by then → `failed` too), clears `next_retry_at` (handed out once), then sends the stored bytes as the row's own attempt (1), through the same `send()` as `redeliver()`
- `sanitize_headers( array $raw ): array<string,string>` — keep names matching `/^[A-Za-z0-9-]+$/`, drop (case-insensitively) `Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Cookie`, `Authorization`, `Proxy-Authorization`, anything starting `X-Forwarded-`, and any value containing `\r` or `\n`; log each rejection. `Authorization` is accepted from one place only: the `bfag_webhook_request_args` result (Pro presets set it there)
- `sign( string $secret, int $timestamp, string $body ): string` — `hash_hmac( 'sha256', $timestamp . '.' . $body, $secret )`, public static

**`EventBus`** — `__construct( WebhookRepository, WebhookDispatcher, EventRegistry, DeliveryRepository, ?\Closure $clock = null )` — the clock returns the Unix time (a test seam for the budgets; null = `time()`). `FLUSH_LIMIT` = 20, `SHUTDOWN_BUDGET_SECONDS` = 15, `FLUSH_BUDGET_SECONDS` = 20, `HOOK` = `bfag_cron_flush_pending`.
- `register_hooks(): void` — for each event in `enabled_events()` that `exists()`, `add_action( hook, closure, 10, accepted_args )`; also `add_action( 'shutdown', [ $this, 'flush' ], 1 )` and `add_action( HOOK, [ $this, 'flush_pending' ] )`
- `handle( string $event, array $hook_args ): void` — return if `Plugin::$dispatching`; `payload()` null → return; push `[ $event, $payload ]` onto `$pending` (dedupe by event + object id within the request). **F9:** under `WP_CLI` or `wp_doing_cron()` a queue that has grown past `FLUSH_LIMIT` is flushed at once, so a long import never holds every payload in memory; a web request always waits for shutdown
- `flush(): void` — nothing pending → return. Otherwise first `fastcgi_finish_request()` when it exists and `apply_filters( 'bfag_webhook_finish_response', 'cli' !== PHP_SAPI )` is true (the response is handed to the web server before any delivery); then set `Plugin::$dispatching = true`; for each pending item, for each webhook `for_event()`: the first `FLUSH_LIMIT` deliveries are `dispatch()`ed now — while fewer than `SHUTDOWN_BUDGET_SECONDS` of wall clock have passed since the flush began (PN5: twenty sends at the five-second timeout against a dead endpoint held a PHP-FPM worker 100 s) — every further one is written through `DeliveryRepository::create()` as `pending` with `next_retry_at = now` (attempt 1, the encoded payload) and ONE `wp_schedule_single_event( time(), HOOK )` is scheduled (deduped on `wp_next_scheduled()`); finally `Plugin::$dispatching = false`, `$pending = []`
- `flush_pending(): void` — the cron handler: `DeliveryRepository::pending( FLUSH_LIMIT )` → `WebhookDispatcher::dispatch_pending()` each under the guard, batch after batch within `FLUSH_BUDGET_SECONDS` of one run (PN4: one batch per cron spawn drained ~20 rows a minute); the budget is checked before every row, and a run that stops with rows left — mid-batch, or a full batch as the budget runs out — schedules the single event again; a short batch ends the run with no re-arm. A row stays selectable until `dispatch_pending()` clears its due time. Queued rows depend on WP-Cron; one the cron never reaches is pruned after a day
- `pending(): array` (tests)
